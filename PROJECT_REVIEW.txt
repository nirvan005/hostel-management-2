====================================================================
HOSTEL MANAGEMENT SYSTEM — AUDIT, RESUME VERIFICATION & REVIEW
====================================================================

====================================================================
PART 1 — UNDERSTAND THE PROJECT
====================================================================

1. Folder Structure
-------------------
The repository is structured as a standard MERN stack application with two primary subdirectories:
- `client/`: Vite-based React Single Page Application (SPA).
  - `src/components/`: Modular React components divided into domain subfolders (Admin, Student, etc.).
  - `src/pages/`: Page-level layout components (`InitialPage`, `InitialLayoutAdmin`, `InitialLayoutStudent`).
  - `src/auth/`: Contains `AuthContext.jsx` for global user session state management.
- `server/`: Express backend API application.
  - `config/`: Contains MongoDB connection configuration (`db.js`).
  - `controllers/`: Request handling and database operations (`auth`, `room`, `student`, `payment`, `checkInOut`, `admin`).
  - `models/`: Mongoose schemas (`users`, `student`, `admin`, `rooms`, `requests`, `payments`, `checkin_checkout`).
  - `routes/`: Express router definitions mapping paths to controllers.
  - `middlewares/`: Empty directory (no route protection or validation middleware implemented).

2. Overall Architecture
-----------------------
Monolithic Client-Server architecture. The client is a React SPA that communicates with a Node.js/Express backend via HTTP REST APIs using Axios. The backend interfaces with MongoDB Atlas via Mongoose ORM.

3. Frontend Architecture
------------------------
- Framework: React 18 with Vite.
- Styling: Bootstrap CSS + custom CSS files (`App.css`, `index.css`).
- Architecture: Component-based. State is predominantly localized using React `useState` and `useEffect`.
- Authentication Context: `AuthContext.jsx` manages user state (`isAuthenticated`, `userId`, `name`, `role`).

4. Backend Architecture
-----------------------
- Framework: Express.js running on Node.js.
- Architecture: Controller-Route pattern. Lacks a dedicated Service layer or Data Access Layer (DAL); controllers directly perform Mongoose queries and handle HTTP responses.
- Database Connection: Asynchronous connection established in `server/config/db.js` using Mongoose.

5. Authentication Flow
----------------------
- Authentication is JWT-based.
- Signup: `/auth/signup-admin` (requires admin key validation) and `/auth/signup-student` store bcrypt-hashed passwords in the `users` collection.
- Login: `/auth/login-admin` and `/auth/login-student` verify credentials and issue `access_token` and `refresh_token` attached to `httpOnly` HTTP cookies.
- Session Persistence: `/auth/checkLogin` endpoint verifies the `access_token` cookie on frontend load.
- Logout: `/auth/logout` clears HTTP cookies.

6. Authorization (RBAC)
-----------------------
- User roles (`admin`, `student`) are stored in the database `users` collection.
- CRITICAL GAP: There is ZERO authorization enforcement on API endpoints. The `middlewares` directory is empty. API routes (`/student`, `/room`, `/payment`, etc.) are completely exposed without token or role checking.

7. Database Schema (Mongoose Models)
-----------------------------------
- `User`: `name`, `username` (unique), `password` (hashed), `phone`, `email`, `role` (enum: "admin", "student"), `refreshToken`.
- `Student`: `student_id` (User ref, unique), `address`, `fathers_name`, `mothers_name`, `allocation_id` (unique), `parent_phone`, `room_id` (Room ref), `start_date`, `end_date`.
- `Admin`: `admin_id` (User ref, unique), `hall_no`.
- `Room`: `room_no`, `capacity`, `occupancy`, `status` (enum: "vacant", "occupied"), `floor_no`.
- `Request`: `user_id` (User ref), `address`, `fathers_name`, `mothers_name`, `parent_phone`, `requested_room_id` (Room ref), `request_date`, `status` (enum: "pending", "approved", "rejected"), `rejection_reason`, `type` (enum: "new", "change").
- `Payment`: `amount`, `payment_date`, `student_id` (User ref), `status` (enum: "Paid", "Unpaid"), `sem`.
- `CheckInOut`: `checkin_time`, `checkout_time`, `student_id` (User ref), `room_id` (Room ref).

8. API Structure
----------------
Resource-oriented endpoints exposed on port 4000:
- `/auth`: Authentication endpoints (`signup-admin`, `login-admin`, `signup-student`, `login-student`, `checkLogin`, `logout`).
- `/student`: Student management (`/`, `/assigned-students`, `/unassigned-students`, `/add-student`, `/remove-student`, `/:room_no`).
- `/admin`: Admin metadata (`/`).
- `/room`: Room and request handling (`/rooms`, `/room-request`, `/change-room-request`, `/change-room`, `/get-change-room`, `/get-new-room`, `/get-all-change-requests`, `/get-all-new-requests`, `/approve-request`, `/assign-room`, `/floors`).
- `/payment`: Payment processing (`/`, `/student`, `/pending`, `/mark-paid`).
- `/checkinout`: Check-in/out records (`/`).

9. State Management
--------------------
- React `useState` & `useEffect` for local component state.
- React Context (`AuthContext`) for user session persistence across components.

10. Routing
-----------
- Client: `react-router` (v6) handles SPA navigation.
- Server: Express `Router` instances mounted in `server/index.js`.

11. Business Logic & Controllers
--------------------------------
Business logic resides entirely inside controllers (`auth.controller.js`, `room.controller.js`, `student.controller.js`, `payment.controller.js`, `checkInOut.controller.js`, `admin.controller.js`).

12. Services & Middlewares
--------------------------
- Services: None.
- Middlewares: None implemented (folder is empty).

13. Environment & Deployment
----------------------------
- `.env` configuration at repository root storing `MONGO_URI`, `ADMIN_KEY`, `ACCESS_TOKEN_SECRET`, `ACCESS_TOKEN_EXPIRES_IN`, `REFRESH_TOKEN_SECRET`, `REFRESH_TOKEN_EXPIRES_IN`.
- Deployment: No Docker, CI/CD scripts, or deployment manifests present.

PART 2 — FEATURE AUDIT
====================================================================

1. Authentication (JWT): ✅ Complete
   - Login, signup, token signing, cookie storage, checkLogin, logout endpoints exist and function.

2. Room Allocation: ✅ Complete
   - Room request creation, admin assignment (`assignRoom`), and database record updates are fully implemented.

3. Room Change Requests: ✅ Complete
   - Request creation (`changeRoomRequest`), admin fetching, and approval/rejection (`approveRequest`) logic exist.

4. Payment Management: ⚠ Partially Implemented
   - Admins can query paid/pending lists and batch update a student's status to "Paid". However, there is no payment gateway integration, partial payment handling, or transaction receipt generation.

5. Check-In / Check-Out Workflows: ⚠ Partially Implemented
   - Reading and formatting check-in/out logs (`getCheckInOut`) is implemented. However, there are no endpoints or UI components to actually perform/record check-in or check-out actions.

6. Role-Based Access Control (RBAC): ❌ Missing
   - Roles exist in MongoDB, but no backend middleware enforces role authorization. API routes are publicly reachable.

7. Server-Side Validation: ❌ Missing
   - Controllers directly pass `req.body` parameters into queries/models without schema validation libraries (e.g., Joi, Zod).

8. Occupancy Analytics: ❌ Missing
   - The UI shows a floor-by-floor list of rooms styled red/green. There are no aggregate analytical metrics, graphs, or statistical summaries.

9. Search & Filtering: ⚠ Partially Implemented
   - Implemented exclusively on the client-side via JavaScript `Array.filter()`. Backend APIs return full, unfiltered collections.

10. Pagination: ❌ Missing
    - Database queries return full datasets without `skip`/`limit` pagination. Frontend renders all records simultaneously.

11. Automated Email Notifications: ❌ Missing
    - No email service integration (e.g., Nodemailer, SendGrid) exists anywhere in the repository.

PART 4 — ENGINEERING REVIEW
====================================================================

1. Missing Authorization Middleware (Security Vulnerability)
   - Why it matters: API endpoints lack middleware checks to verify user identity or role.
   - Production impact: Unauthenticated clients can execute privileged actions (e.g., delete/assign students, change room statuses).
   - Difficulty to fix: Easy.
   - Solution: Implement a custom JWT/RBAC middleware using `jsonwebtoken` and mount it across Express routes.

2. Fat Controllers / Monolithic Architecture (Architectural Problem)
   - Why it matters: Controllers blend HTTP parsing, query construction, aggregation pipelines, and response handling.
   - Production impact: Reduced testability, code duplication, and maintenance bottlenecks.
   - Difficulty to fix: Medium.
   - Solution: Refactor logic into a dedicated Service layer (`StudentService`, `RoomService`, `PaymentService`).

3. Client-Side Data Processing (Performance Issue)
   - Why it matters: Endpoints load entire MongoDB collections into memory, sending full datasets to the frontend for client-side filtering.
   - Production impact: High latency, unnecessary server memory consumption, and network saturation under real-world dataset sizes.
   - Difficulty to fix: Medium.
   - Solution: Implement server-side search (`$regex`) and pagination (`limit`, `skip`) in database queries.

4. Unhandled Errors and Missing Input Validation (Quality & Reliability Issue)
   - Why it matters: Controllers pass unvalidated `req.body` directly to database calls and catch errors with generic `res.status(500).send(err)`.
   - Production impact: Potential database corruption, app crashes, and exposure of internal database error traces to end users.
   - Difficulty to fix: Easy.
   - Solution: Use schema validation libraries (Zod or Joi) on incoming requests and centralized error-handling middleware.

5. Direct Axios Calls without Centralized Configuration (Code Duplication)
   - Why it matters: Frontend components instantiate hardcoded Axios calls (`axios.get("http://localhost:4000/...")`).
   - Production impact: High friction when changing API host environments; lack of global request/response interceptors.
   - Difficulty to fix: Easy.
   - Solution: Create an Axios API client instance with `baseURL` configured via environment variables (`import.meta.env`).
